- GPU run started at 12 it/s (0.083 s/it) — expected for a ~1.6M param VAE

- Likely causes: .item() calls forcing CUDA sync every iteration,

- Then fluctuated between 0.082–0.094 for the remaining 97,500 steps

- The remaining ~200,000 iterations would have produced no improvement
- Conclusion: scGen training was effectively done within the first 1–2 hours

2. UNDERSTANDING THE TRAINING PIPELINE
========================================

scGen architecture:
- Autoencoder: 1000 → 512 → 512 → 50 (encoder) → 512 → 512 → 1000 (decoder)
- Loss: MSE reconstruction + beta * ||latent||^2 (beta=0 in config, so pure MSE)
- ~1.6M parameters total

Data split (toggle_ood, mode=ood):
- train: 80% of non-rat cells (human, mouse, pig) — model trains on these
- test: 20% of non-rat cells — eval loss computed every 2,500 steps
- ood: 50% of rat cells — reserved for downstream evaluation
- ignore: 50% of rat cells — discarded
- Rat is completely unseen by both scGen and CellOT during training

Training mechanics:
- 1 iteration = 1 step = 1 batch of 128 cells (not 1 epoch)
- DataLoader with shuffle=True, num_workers=0 (default, single-threaded)
- Batches sampled without replacement within each epoch; reshuffled at epoch start
- Training loss = MSE on the training batch just processed
- Eval loss = MSE on a test batch (no gradients), used to select model.pt
- Training loss fluctuates per-batch; does NOT monotonically decrease
- Eval loss is what matters — measures generalization to unseen data

Checkpointing/resuming:
- last.pt saved every cache_freq steps (10,000 for scGen, 1,000 for CellOT)
- Contains model weights, optimizer state, and step number
- On restart, code loads last.pt and resumes from the saved step
- model.pt contains the best model (lowest eval loss / MMD)

HDF5 scalars file:
- Binary file at cache/scalars, not human-readable in a text editor
- Read with: pd.read_hdf("cache/scalars", key="train") and key="eval"
- Contains logged metrics at logs_freq and eval_freq intervals


3. CELLOT TRAINING SETUP
==========================

CellOT uses the frozen scGen encoder to embed all cells (including rat)
into 50-dim latent space, then trains optimal transport maps in that space.

CellOT architecture:
- Two networks (f and g) with hidden_units [64, 64, 64, 64]
- Input dim: 50 (scGen latent)
- ~31k parameters total — very small
- n_inner_iters=10: 10 g-updates per f-update per outer iteration

Previous CellOT run (cross_species_ood, no scGen embedding):
- Ran on 1000-dim raw gene expression
- Completed 100k iterations in ~21 hours on CPU at ~1.3 it/s
- Best MMD: 0.015835 at step 2,000

CellOT with scGen embedding:
- Operates on 50-dim latent space → much faster per iteration
- ae_emb.path points to scGen results directory
- Code encodes ALL cells (including ood rat) through scGen before splitting


4. GPU VS CPU ANALYSIS
========================

For models this small (~31k params for CellOT, ~1.6M for scGen):
- GPU provides negligible speedup over CPU
- Bottleneck is Python overhead, data loading, and CPU→GPU transfer latency
- GPU overhead (11 data transfers per outer step for CellOT) exceeds compute savings
- Recommendation: use shared (CPU) partition for this model size, save GPU for larger models

SLURM partitions considered:
- shared: CPU-only, usually short queue, 3-day limit
- gpu: A100 GPUs, longer queue wait, 3-day limit
- gpu_requeue: scavenges idle GPU nodes, shorter wait, but jobs may be
  killed and requeued (checkpointing handles this gracefully)
