# Research log — 2026-07-30 / 2026-08-03
# Environment modernization: one conda env that reads BOTH h5ad formats
#                            and runs the models (CellOT_v3)

## Decision

ADOPT CellOT_v3, gated on one one-line change to the vendored cellot package.

A single environment that reads old (anndata 0.7) and modern (anndata 0.12)
.h5ad files AND runs the trained models is achievable, and CellOT_v3 is that
environment. Every validation check below passed. The cross-environment file
barrier is removable, not merely workaround-able.

The one blocker found is in OUR repo, not in a dependency, and the fix is
backward-compatible with python 3.9 (verified), so it can land without
touching the existing envs.

## Problem being solved (context, already diagnosed — not re-derived here)

  analysis    python 3.12, anndata 0.12.10, scanpy 1.12   -- data prep
  CellOT      python 3.9.5, anndata 0.7.6, torch 1.11.0+cu102, scanpy 1.8.1,
              numpy 1.19.5, pandas 1.2.5                  -- hub, training, eval
  CellOT_gpu  python 3.9.23, anndata 0.7.6, torch 2.3.1+cu121, scanpy 1.8.1

anndata 0.7.6's EncodingVersions enum has exactly one member, 'raw'. Modern
anndata tags every group with an encoding-type (dict / dataframe / categorical
/ csr_matrix), so 0.7.6 raises KeyError: 'dict' on ANY modern file. The
existing workaround, scripts/h5ad_to_v07.py, reads with h5py and rewrites with
anndata 0.7. It stays useful and is NOT being removed; CellOT_v3 is the
permanent fix alongside it.

### Design choices and why

- python 3.11, not 3.12: keeps a wide wheel selection and avoids the distutils
  removal. 3.10 would also work.
- torch 2.3.1+cu121, byte-identical to what CellOT_gpu already runs. This
  deliberately holds the GPU stack constant so that any numerical difference
  observed is attributable to numpy/pandas/python, not to torch. It also means
  CellOT_v3 is a drop-in for CellOT_gpu on the GPU side.
- numpy 1.26.4, not numpy 2.x: torch 2.3.1 is compiled against numpy 1.x and
  emits a hard "module compiled using NumPy 1.x cannot be run in NumPy 2.x"
  failure under numpy 2. Moving to numpy 2 requires torch >= 2.4.1 and is a
  separate, larger decision.
- anndata 0.10.9, not 0.11/0.12: 0.10.x is the newest line that still ships
  `anndata.read` as a deprecated alias. cellot/data/cell.py:59 calls
  `anndata.read(path)`; anndata 0.11 removed it. Choosing 0.10.9 keeps the
  required repo change to ONE line instead of two. 0.10.9 reads both formats,
  which is the whole point.
- scanpy 1.10.4: the matching scanpy line for anndata 0.10 + pandas 2.

### Check B — import the vendored cellot package                 FAIL, then PASS

First attempt failed:

  File ".../cellot/utils/helpers.py", line 1, in <module>
      from collections import MutableMapping
  ImportError: cannot import name 'MutableMapping' from 'collections'

MutableMapping moved to collections.abc in python 3.3; the `collections`
alias was removed in python 3.10. This is the ONLY python-3.10+ breakage in
the vendored package — a grep over cellot/ for the usual removals
(`from collections import`, np.float/np.int/np.bool/np.object, imp,
time.clock, inspect.getargspec) turns up nothing else. The two other
`from collections import namedtuple` hits (models/cellot.py:3, models/ae.py:3)
are fine.

Required change, one line:

  cellot/cellot_gpu/cellot/utils/helpers.py:1
  -   from collections import MutableMapping
  +   from collections.abc import MutableMapping

Verified back-compatible: `from collections.abc import MutableMapping` imports
cleanly under the legacy CellOT env's python 3.9.5, so this can land on main
without disturbing CellOT / CellOT_gpu / analysis.

Per instructions this change was NOT applied to the repo. To finish validating
without editing the repo, a throwaway overlay was used:

### Check D — numerical agreement, old env vs new env                   PASS

This is the check that matters most, and it is clean.

Setup: 400 synthetic mouse cells over a 3,500-gene panel built from REAL
ENSMUSG ids — 3,000 sampled (seed 20260730) from
scripts/.biomart_ortholog_cache.csv plus 500 syntactically valid ENSMUSG ids
deliberately absent from the cache, so the ortholog mapping actually has to
drop things. Counts are Poisson with gene-specific means and cell-specific
depth (total 1,909,017 counts, 56.1% zeros, max 56). The matrix is handed to
both envs as a plain .npz so the comparison isolates the model code path
rather than the h5ad interchange (tested separately in Check A).

Both envs then ran predict_new_input.sh phase 1 (ENSMUSG -> ENSG via the
BioMart cache, projection onto the 1,000-gene atlas axis, normalize_total
1e4, log1p) and phase 3 (scgen shift, and impact_cellot ICNN transport).
Ortholog coverage came out at 200/1000 (20.0%) in BOTH envs — identical, so
the mapping logic is version-stable.

Two results inside this deserve to be called out:

1. The scGen shift vector is BIT-IDENTICAL (max|diff| exactly 0.0). That

## Recommendation

Adopt CellOT_v3 as the single env for the hub, eval, prediction and
(unvalidated on hardware, see below) GPU training. Keep CellOT and CellOT_gpu
in place untouched as the fallback until a GPU training run has been
reproduced on CellOT_v3.

Migration, in order:

  1. Land the one-line helpers.py fix on main. Harmless to the existing envs.
  2. Run one GPU training job on CellOT_v3 (see "not verified" below) and
     compare its loss curve / final checkpoint against a CellOT_gpu run.
  3. Point the `hub` wrapper at CellOT_v3: `hub:15,32,33,38`. The wrapper is
     the only thing that must change for `./hub` to work; the CLI itself is
     already byte-identical under both interpreters.
  4. Update the hardcoded interpreter paths:
       scripts/predict_new_input.sh:38    CELLOT_PY=
       scripts/biomart_watchdog.py:31     CELLOT_PY=
       speciesOT/baseline/analysis/19_uncapped_cd8_ood_data_prep.py:66
  5. Once CellOT_v3 is the default, phase 2 of predict_new_input.sh (the
     v07 round-trip, lines 148-215) becomes unnecessary — CellOT_v3 reads the
     analysis env's output directly. Delete it from the script only after
     step 2 passes. Keep scripts/h5ad_to_v07.py: it is still the way to make
     a file readable by the legacy envs, which are staying.
  6. Update docs/hub_usage.md:24,368 and docs/mentor_runbook.md:218,243,458.
  7. Consider collapsing `analysis` into CellOT_v3 as well. Not attempted
     here — CellOT_v3 has scanpy 1.10.4 vs analysis's 1.12, and `./hub prep`
     HVG selection was not tested under it. Treat as a separate task.

Also worth doing once adopted: pin this stack in a requirements file next to
cellot/cellot_gpu/requirements-gpu.txt so it is reproducible, since it was
built by explicit pins rather than a solver file.

## What was NOT verified

State plainly, because a partially validated env is a partially validated env:

- GPU. Everything ran on a CPU node with no nvidia-smi. torch 2.3.1+cu121 is
  installed and is the identical build CellOT_gpu already uses on H100/H200,
  so the risk is low, but CUDA was never exercised and no training step was
  run. This is the one gap that should close before CellOT_v3 becomes the
  default for training.
- Training. Only inference/restore paths were tested. No optimizer step, no
  checkpoint WRITE, no cellot/train/*.py path.
- `./hub prep`. The prep path (HVG selection, prep_backed.py, the 43 GB atlas)
  was not run under CellOT_v3. scanpy 1.10.4 != the analysis env's 1.12.
- `./hub` subcommands beyond `list` and `scorecard` — generate, metrics,
  vault, card, show, compare — were not run.
- The deferred pandas items above (applymap, the fillna inplace) sit on code
  paths none of these checks touch.
- numpy 2.x. Explicitly avoided, not tested; it needs torch >= 2.4.1.
