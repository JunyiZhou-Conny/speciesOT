3.4 Merge hazard verdict
------------------------
  MECHANICALLY ROUTINE, STRUCTURALLY HAZARDOUS.

  Routine, because: with unrelated histories git treats every path as
  added-on-one-side. Only paths present in BOTH trees can conflict, and there is
  exactly one such path (.gitignore). A `merge --allow-unrelated-histories`
  would produce a single textual conflict, resolvable in a minute.

  Hazardous, because the result is not what anyone wants:
    (a) It fabricates a shared ancestry that never existed, permanently. Every
        future `git log`/`blame` on the combined repo shows two disjoint roots
        stitched at one commit.
    (b) It dumps 36 loose notebooks into the root of a repo whose AGENTS.md
        "where things live" map has no slot for them. The mentor's e*.ipynb
        expect to sit beside speciesot_helpers.py at top level; main's layout
        would silently satisfy that (both land at root) but the resulting root
        directory becomes 20 notebooks + 11 project dirs.
    (c) It is being computed against a STALE josh/main. The real tip is
        8f0a7d82, unknown content. Merging a stale ref then pushing is how you
        clobber a collaborator.
    (d) The `cellot` branch/worktree already IS the legitimate bridge into the
        mentor's repo and would be bypassed.

  Verdict: do not merge josh/main into main.

===============================================================================

The goal is not "one tidy history". The goal is: Joshua can clone something,
follow one document, and produce human predictions from BCG mouse cells on HIS
account. Optimize for that.

RECOMMENDED — Option (iii): publish on mine/main, hand over by URL, and open a
cross-repo PR only as a review artifact.

  Ordering (each step is a gate; do not batch them):

  S0. `git fetch josh`  (read-only w.r.t. working tree; updates tracking refs)
      Re-run `git log --oneline f0585b4..josh/main` and re-read section 3.

  S6. `git push mine main`.

  S7. Hand over: send the mine/main URL + the README + docs/cursor_fasrc_handout.md.
      Tell him to clone from JunyiZhou-Conny/speciesOT, not from his own repo.

  S8. Separately and optionally, push a branch to josh (e.g.
      `git push josh main:junyi-hub-2026-07`) and open a PR josh:junyi-hub-2026-07

      into his main. NEVER force-push; AGENTS.md forbids it.

  blob in history cannot be removed without a rewrite, which is forbidden here).
  S2 before everything else because a broken `./hub` makes the rest untestable.

  What can still go wrong:

      /n/home01/jzhou1125/miniforge3 (hub:16) and fails on his account. This is
      the #1 predictable failure. Section 5.2 fixes it; treat as part of S2.
    - He runs scripts/predict_new_input.sh: it needs checkpoints and BioMart
      caches that are gitignored and will not be in his clone. Section 5.3.
    - He clones to a different directory and eight modules with
      WORKSPACE_ROOT = Path("/n/holylabs/.../junyizhou/speciesOT") silently read
      Junyi's files instead of his. This one is worse than a crash because it
      LOOKS like it worked. Section 5.2.

ALTERNATIVE (i) — commit to mine/main only, mentor uses the fork.
  This is S0-S7 without S8. Pros: least risk, fastest, zero chance of disturbing
  the mentor's repo. Cons: the mentor's repo stays the "official" one while the

  he later wants it in JoshuaPrice/speciesOT the problem is unchanged and older.
  Verdict: acceptable fallback. It is strictly a prefix of the recommendation,

  Pros: one repo containing both lineages; the mentor's tb/ BCG notebooks would

  copy the two notebooks in with attribution rather than merging 75 commits of

ALTERNATIVE (iv), worth considering — hand over via the `cellot` branch.
  josh/cellot IS related to josh/main (merge base a7f7301) and already carries
